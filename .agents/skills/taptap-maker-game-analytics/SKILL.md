# TapTap Maker 埋点与广告观看统计

## 云端执行

先读[云端使用说明](../../../docs/taptap-cloud.md)，确认真实游戏目录。来源项目的路径、函数和测试脚本只作参考，实施时核对当前源码与接口。

建立能解释玩家流失和广告使用情况的数据；修改前确认目标项目、当前云接口、数据键和查询口径。

## 先定义统计合同
每项明确事件ID/版本、触发时机、人数或次数、去重范围、来源/模式、统计时间范围、测试账号处理、读取方法与失败表现。
- 首次进入、教学完成、关卡通过、模式开放、章节到达：账号级里程碑，重复登录或换机不重复计人。
- 开局、结算、主动退出、广告成功：可重复事件，按局次/请求ID去重。
- 章节运营天数与现实游玩天数分开；“10F满20天”是该层已完成天数，不能误用总运营日或新层天数。
- 分母必须明确。累计关卡完成人数差只能说明尚未通过，不能直接命名为永久流失；不能据此声称次日留存。
- 真正留存需要首次日期与回访日期/同一批用户；SDK无此能力时说明限制。

## 写入
- 固定有限的事件白名单，项目独立且带版本的键。使用当前接口支持的批量上报，避免渲染循环逐项请求。
- 若账号内标记可用 SetInt(1)，它适合里程碑幂等重试；成功回调后才标为已同步。失败保留待发送并退避，切账号清理会话缓存。
- Add型累计写入超时可能已经成功；无幂等凭证时不能无限重试并声称无重复。明确 best-effort 局限或采用已授权的可靠事件后端。
- 老存档可根据真实进度补报“已到达”，不能编造历史事件日期、曾看广告次数或准确教学路径。
- 埋点失败不阻塞游戏或发奖；日志与内存队列有界。

## 广告观看统计
- 统一广告成功入口携带稳定 source ID；结算、福利、各商品分开。计数应在去重后的平台成功分支，测试绕过排除。
- “成功观看数”与“成功发奖数”分别定义，不把点击次数当观看次数。若诊断加载，可另加请求/展示/取消/失败/超时与耗时，不能声称来源游戏已经都有。
- 明确营业日时区与刷新点，优先项目可信时间服务；离线降级须可辨认。游戏内直通日期不能改变现实广告统计日。
- 日期键会增长，规划查询窗口/保留周期并遵守平台配额，避免永久无限造键。

## 查询与页面
- 验证 GetRankTotal 等API的确切语义（排名人数不等于观看次数之和）。
- 前N名累加是截断样本，标注“已加载人数/样本或至少值”；不同来源的前N账号集合可能不同，不能简单算全体用户转化。
- 全量需求用官方分页能力或真实聚合接口，并处理边界、并发变化和限流；不把客户端排名查询包装成全量分析后端。
- 异步页面采用请求代号与单项完成标记，忽略旧页回调；异常显示不可用，不能假装为0。列表滚动且关键信息不省略。
- 运营数据入口按项目要求控制可见性；客户端隐藏入口并不是后端鉴权。

## 验证
用伪云回调验证重复登录、失败重试、重复回调、旧存档补报、跨营业日、超过查询上限、局次重复结算、切页回调。用已知账号数/事件数核对显示。重置游戏进度不应默认清除运营历史。

来源事件清单与已知限制见 [references/elevator-evidence.md](references/elevator-evidence.md)。
